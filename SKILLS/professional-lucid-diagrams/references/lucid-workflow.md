# Preserve meaning before styling

## Source and capability preflight

1. Inspect the actual referenced files, images, or linked content before generation. Verify extensions, format, page counts, and selected revisions; filename or existence does not establish which revision is latest.
2. Record provenance: source location, revision, inspected pages, and any agreed precedence. Compare hashes before replacing binary revisions; preserve external originals and record old/new hashes rather than silently overwriting the evidence.
3. Current explicit user edits outrank stale diagram assumptions. Flag conflicting source requirements rather than choosing silently. Include requirement codes only when relevant or requested; never restore explicitly removed internal FP IDs from an older source.
4. Inspect tool descriptions and capabilities first, then read the provider-required resources/schema freshly before each applicable operation. These local instructions do not replace provider hard gates. Discover valid shapes and IDs instead of guessing them.
5. If a source SVG exists, use the provider's SVG conversion route. If unavailable, stop that generation path and report the capability blocker; do not hand-author a substitute import. Do not invent add-page, PDF-export, or integration abilities.

If necessary source content is inaccessible, ask one short question requesting it, then wait. Do not create generic placeholders. Do not send the user on an export task before fixing the design/plan; request a user-assisted export only if necessary, available, and within the agreed workflow.

## Plan only when needed

- For ordinary concrete creation with sufficient source, proceed using sensible stated defaults; do not impose a planning interview.
- When asked to collaborate, clarify the meaningful uncertainty, offer a concise outline, and wait for direction. Ask only one question per turn.
- For a batch, select one representative prototype that exercises density, branching, labels, and branding. Confirm its layout and target-size readability before generating the remaining diagrams. Reuse that approval; do not request ceremonial approval for every sibling.
- Stop for significant semantic or scope changes. Prototype approval does not authorize extra pages, different packaging, external sharing, or publication.
- If Lucid is the approved medium, stop unused alternative experiments. Use TikZ only when explicitly requested, not as an automatic fallback.

## Structural verification

Maintain a source-to-output inventory. For each unique node, record its identity, label, type/state, and destination page. For each edge, record source, destination, direction, label, kind, and multiplicity. Preserve parallel edges, isolated nodes, state routes, and semantic distinctions. Verify unique node coverage and edge coverage separately; repeated anchors across general/detail views are references, not additional semantic nodes.

Use meaningful shapes for decisions. Distinguish operational flows, dependency arrows, and state transitions through an explicit consistent visual language. Crossings must not imply joins. Report intended omissions or abstractions and obtain approval when they change meaning.

## Page and document contract

Keep a compact manifest with diagram family, version/source revision, actual document ID/link, page number, role (general/detail), export filename, integration label, and verification status. Never invent IDs or export paths. Keep general and detail documents/versions distinct.

A complete overview may legitimately occupy two complementary general pages if approved. State that consistently: neither page alone is complete. Use honest captions such as partial/general/detail; verify collective coverage. Do not multiply pages to conceal an unresolved layout problem.

If adding pages is unavailable, propose companion documents and explain the tradeoff: separate navigation rather than one edited multipage document. Obtain approval before changing page count or delivery mode; never claim a companion was added to the original document.

## Bounded completion

Use at most two correction/review rounds by default. After that, surface the concrete unresolved issue and proposed next action rather than looping or declaring success. Safe corrections within the approved scope need no repeated approval; semantic or packaging changes do.

Report only observed states: created; structurally verified against named revision; visually reviewed at specified target dimensions; integrated into named source; compiled and inspected for named output revision. Never use blanket “professional print-ready” language without actual target evidence. Keep delivery short and actionable; perform authorized safe packaging rather than handing over a long manual filename-copy list.
